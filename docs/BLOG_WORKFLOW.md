# 学术博客维护规范

## 内容与文件约定

- 永久网址使用 `blog/<slug>.html`，slug 为小写英文 kebab-case，如 `solov2`。已发表的网址不改名；确需迁移先保留旧入口。
- `content/<slug>.html` 保存正文，`data/posts.json` 保存作者、标题、日期、发表状态、版本、论文与代码链接；`templates/article.html` 和 `assets/css/article.css` 统一新文章结构和排版。
- `blog/solo.html` 与 `blog/solov2.html` 是生成结果，正文修改应在 `content/` 中完成；修改后重新生成并一起提交。
- FCN、U-Net 是既有手写文章，标记为 `legacy: true`，生成器不写入这些文件。原正文、独立样式和网址全部保留。若之后迁入新模板，必须人工审查完整正文差异，不能用摘要重写旧文。
- 首页 `BLOG:AUTO:START` 到 `BLOG:AUTO:END` 之间为新增文章自动目录。原有两条文章目录和首页其他区域不由脚本重建。
- 图片统一使用 `assets/figures/<slug>/`。每张图在 `assets/figures/sources.json` 记录原始来源、创作类型、许可核验结果和日期。新文章图片可点击查看原尺寸。
- 文章阅读顺序按 `data/posts.json` 排列；新文章页的上一篇、下一篇由生成器建立。旧文章自身导航暂保留原样。

## 每篇论文的核验与分析

先核验原文、作者、正式出版记录和作者链接的代码仓库。发表状态只用有证据支持的“正式发表”“已接收”“预印本”，不要因存在 arXiv 链接就标成仅预印本。记录首次预印本年份与正式会议年份，避免版本混用。

默认采用简短的图解阅读：核心想法 → 原文方法图 → 几步流程 → 与前作的关键区别。以图片和直观的流程卡片承担解释，正文只补充读图所需的信息。中文为主，保留必要术语。除非用户另有要求，不加入实验表格、实验分析、消融建议或长篇研究延伸。作者、版本和许可放入可展开资料区，全文和官方代码入口保持直接可见。

引用数值时逐项核对：表号、数据集与 split、backbone、训练周期、输入尺度、指标单位、硬件和速度计时边界；未核验的数值不写。COCO AP 不直接与核分割 AJI / PQ 比较。没有本地复现实验时明确写“作者报告，本文未复现”。同一词如“reliability”必须给出实际定义，不能用命名代替机制证据。

消融应检验具体主张、控制变量并排除替代解释：等参数普通模块、分辨率和训练预算、结构与额外监督、NMS 前后候选召回、密度分组、多个随机种子。研究空白是待验证问题，不自动构成新颖性证明。

## 图片权限

免费可读、arXiv 可下载、代码开源，都不自动说明论文原图获准转载。优先核验图片本身、论文或项目页面的明确许可及署名要求，并保留证据链接。无法确认时，独立设计原创概念图，说明依据哪篇论文哪一节；不得只描摹原图布局并当成原创。不给原创图虚构论文实验数值，也不把代码许可证套到论文插图。

SOLO 系列现采用两篇 arXiv v3 中的原图：两版均明确标注 CC BY-NC-SA 4.0，可用于本站非商用学习介绍，须署名、链接原文与许可、说明修改，并使改编沿用同一许可。实际选用 5 个原图文件，未改动图像字节；Fig. 2(a)/(b) 分开展示。此前 4 张原创 SVG 留存，不再用于正文。许可判断针对 arXiv 版本，不从 Springer 出版页面或代码仓库的许可推断。`sources.json` 记录逐图来源与审查结果，不改变整个网站或第三方内容的许可。

## 添加下一篇文章

1. 核验来源，在 `data/posts.json` 中添加一条记录（复制 SOLO 条目字段，按真实情况填写，不使用 `legacy`）。`series` 可填写所属系列编号或“专题阅读”。
2. 编写 `content/<slug>.html`，提供清晰的章节锚点、文内引用、末尾来源、正文图注，以及研究假设的边界说明。
3. 将图片保存到 `assets/figures/<slug>/`，更新 `sources.json`；使用 `<figure>`、描述性 `alt`、宽高与图注，提供原尺寸图片链接。
4. 执行：

```bash
python scripts/build_blog.py
python scripts/build_blog.py --check
python scripts/check_site.py
python -m http.server 8000
```

5. 在浏览器检查首页及文章，至少查看 375px、390px、768px 和桌面宽度：正文、长标题、目录锚点、图注、表格局部滚动、图片原尺寸链接、上下篇与返回首页。应无整页横向溢出。外部链接遇到 403 / 429 时记录访问受限，不能直接断言论文不存在。
6. 查看 `git diff --check`、`git diff --stat` 和完整差异；确认旧文章没有意外变动。提交生成页面、正文、元数据和图片的同一版本。正常快进提交，不使用 force push。发生远端更新先 fetch 并审查整合。
7. 提交 GitHub 后检查 Pages 构建状态和线上链接。CI 只检查生成一致性与静态资源，不等于线上发布成功；没有推送或构建成功证据时不得宣称已上线。

无需 Node、前端打包工具或线上 JavaScript 即可访问页面。GitHub Pages 继续使用原仓库已有的发布设置，本次不改变域名、发布分支或 hosting 配置。

## 保留的历史问题

- U-Net 页底 `Next: Mask R-CNN` 指向未创建的 `blog/mask-rcnn.html`。检查器把这个精确地址作为已知历史问题报告，不把其他新增死链接加入豁免。原页未修改，后续可完成 Mask R-CNN 精读，或经正文迁移审查后更换导航。
- FCN 尚未采用统一论文链接和图源记录，U-Net 也未补充新规范下的图片与代码元数据。此次没有覆盖旧文章；完善这两篇属于后续迁移任务。
- 首页保留原有的占位邮箱，以及与本仓库账户拼写不同的 GitHub 联系链接。联系信息需要本人确认，不能猜测邮箱或改写身份。

本规范建立可重复的维护流程，不会自行创建周期发布或定时任务。
